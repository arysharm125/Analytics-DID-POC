# VC Compatibility Testing

This directory contains tests that validate compatibility between the Python backend (which generates VCs) and the JavaScript frontend (which verifies them).

## Overview

The VC compatibility testing framework ensures that Verifiable Credentials created by the Python backend can be successfully verified using the JavaScript frontend verification libraries. This is critical for maintaining cross-language compatibility.

## Architecture

The testing process has two phases:

### Phase 1: Python Fixture Generation (Backend)
- Located in: `tests/vc_compat/`
- Generates VCs using the Python `DIDService`
- Exports VCs and DID documents as JSON fixtures
- Creates a manifest listing all generated fixtures

### Phase 2: JavaScript Verification (Frontend)
- Located in: `didcheck/tests/backend-compat/`
- Loads fixtures generated by Python
- Verifies VCs using `@digitalbazaar/vc` library
- Uses the same verification code as the production frontend

## Usage

### 1. Generate Fixtures (Python)

Run the Python tests with the `vc_compat` marker:

```bash
# From project root
pytest -m vc_compat
```

This will:
- Create `tests/fixtures/vc_compat/` directory (gitignored)
- Generate test VCs covering various scenarios
- Export DID documents for all divisions
- Create a `manifest.json` index file

### 2. Run Verification Tests (JavaScript)

The frontend compatibility tests are isolated in their own directory with a separate package.json and test configuration. They will **not** run as part of any generic frontend test suite.

```bash
# Install dependencies (first time only)
cd didcheck/tests/backend-compat
npm install

# Run tests
npm test

# Run tests in watch mode
npm run test:watch
```

Alternatively, from the `didcheck/` root directory:

```bash
npm run test:vc-compat
```

## Adding New Test Cases

To add a new test case:

1. Add a new test function in `test_generate_fixtures.py`:

```python
@pytest.mark.vc_compat
def test_generate_my_new_case(did_service, fixtures_dir: Path, vcs_dir: Path):
    """Generate a VC for my new test case."""
    artefact_input = ArtefactInput(
        external_uid="your-uuid-here",
        division="advisory",
        # ... other fields
    )

    record = did_service.upsert_artefact(artefact_input)
    vc = did_service.issue_artefact_vc(division="advisory", uid=record.version_uid)

    fixture_path = vcs_dir / "my_new_case.json"
    with open(fixture_path, "w") as f:
        json.dump(vc, f, indent=2, default=str)
```

2. Optionally add a specific test in `vcCompatibility.test.js`:

```javascript
test('should verify my new case', async () => {
  const vcPath = path.join(FIXTURES_DIR, 'vcs/my_new_case.json')
  const credential = JSON.parse(readFileSync(vcPath, 'utf-8'))

  const suite = new DataIntegrityProof({ cryptosuite: eddsaRdfc2022CryptoSuite })
  const result = await vc.verifyCredential({
    credential,
    suite,
    documentLoader: testDocumentLoader
  })

  expect(result.verified).toBe(true)
  // Additional assertions...
})
```

3. Regenerate fixtures and run tests:

```bash
pytest -m vc_compat
cd didcheck/tests/backend-compat && npm test
```

## Troubleshooting

### Fixtures not found

**Error**: `Failed to load manifest.json`

**Solution**: Run `pytest -m vc_compat` first to generate fixtures.

### Verification failures

**Error**: `result.verified` is false

**Possible causes**:
1. Signing key mismatch between fixture generation and verification
2. JSON-LD context resolution issues
3. Cryptographic suite configuration differences

**Debug steps**:
1. Check the error details in the test output
2. Verify DID documents have correct public keys
3. Ensure both Python and JS use the same cryptosuite (eddsa-rdfc-2022)

### Module resolution errors

**Error**: Cannot find module '@contexts/...'

**Solution**: Ensure you're running tests from `didcheck/tests/backend-compat/` directory and that `vitest.config.js` path aliases are correct.

## Test Isolation

### Backend (Python)
- Tests use the `@pytest.mark.vc_compat` marker
- Only run when explicitly requested: `pytest -m vc_compat`
- Will **not** run with generic `pytest` command

### Frontend (JavaScript)
- Tests are in a separate directory: `didcheck/tests/backend-compat/`
- Have their own `package.json` and `vitest.config.js`
- Only run when explicitly requested: `npm run test:vc-compat` (from didcheck root) or `npm test` (from backend-compat directory)
- Will **not** run as part of any generic frontend test suite

This isolation ensures:
- Fixtures are only generated when needed
- Tests don't interfere with regular development workflows
- CI can run compatibility tests as a separate job
